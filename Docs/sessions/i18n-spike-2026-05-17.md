# i18n spike — relatório + recomendação

**Data:** 2026-05-17
**Persona dispatch:** Robin (research) + Ted (arquitetura) + Lily (DX/UX)
**Status:** spike (não-código). Recomendação + roadmap.

---

## 1. Por que agora

App hoje é **monolinguagem PT-BR** com termos protocolares fixos em EN
(DRIFT, SPREAD, BURY, nsec, npub, NIP-01..NIP-65). Onboarding, settings,
toasts, errors, banners — tudo em PT-BR hardcoded em JSX e `dialog()`
calls.

Pra adoção global (manifesto §15 anti-censura por país; §29 portabilidade
cross-Nostr-client), i18n é eventualmente requerido. Mas custo de fazer
mal é alto: lock-in de chaves, bundle inchado, workflow de tradução
quebrado, glossário protocolar adulterado.

Este relatório define **arquitetura** + **roadmap**, não shipping ainda.

---

## 2. Glossário protocolar — NUNCA traduzir

Manifesto §29 + CLAUDE.md "Vocabulary mapping" travam que estes termos
ficam congelados em qualquer locale:

- **Protocolo/spec/código (sempre EN):** SPREAD, BURY, kind 9078..9081,
  nsec, npub, NIP-*, DRIFT (no contexto de DRIFT ↑ action)
- **UI verbo PT-BR atual:** "drift" (ação), "sink" (ação), "deriva"
  (substantivo) — estes SÃO traduzíveis pois são UI-layer, mas tradução
  precisa preservar a metáfora hidrológica (ex.: en-US poderia ser
  "drift"/"sink"/"drift" mesmas palavras; es-ES "deriva"/"hundir"/
  "deriva").

LOCK_VIA_TEST existente em `tests/manifesto-conformance.test.ts` trava
glossário protocolar. **Test futuro** (i18n-glossary-conformance) deve
travar que nenhum locale traduz SPREAD/BURY/NIP-*/nsec/npub.

## 3. Avaliação de bibliotecas

Matriz: bundle gz (após tree-shake estimado), runtime, DX, ICU support,
extract-tooling, comunidade. Dados de bundlephobia + repo audits.

| lib | gz | runtime | extract | ICU | RTL | DX | veredict |
|---|---|---|---|---|---|---|---|
| **react-intl (FormatJS)** | ~14 KB | médio | bom | ✅ completo | ✅ | ok mas verbose | rejeitado — bundle alto pra Drift |
| **i18next + react-i18next** | ~8 KB | leve | externo | parcial | ✅ | ok | candidato B |
| **LinguiJS v4** | ~2 KB | leve | macro→AOT | ✅ completo | ✅ | excelente (macros) | **recomendado** |
| **Format-Message** | ~5 KB | leve | parcial | ✅ | ✅ | médio | rejeitado — comunidade pequena |
| **custom Zustand** | <1 KB | leve | manual | manual | manual | trabalhoso | rejeitado — reinventa roda |
| **$localize** | ~3 KB | leve | bom | parcial | ✅ | acoplado a Angular toolchain | rejeitado — fora do stack |

**Recomendação: LinguiJS v4**

Razões:
1. **Bundle minimal (~2 KB)** — Lingui compila macros em strings finais
   no build, runtime só carrega catalog + interpolation primitive.
2. **Macros pegam strings inline** — `t\`bem-vindo ao drift\`` extrai
   automático via `lingui extract`. Sem maintain manual de keys.
3. **ICU completo** — plural/select/gender suportado pra PT-BR + idiomas
   complexos (árabe 6 plural forms).
4. **AOT compile** — zero runtime parsing de ICU strings; mensagem
   compila pra função JS no build.
5. **Tipos TS** — catalog gera types pra strings, autocomplete em IDE.

Trade-off: macros exigem babel/swc plugin no Vite (passo extra no
config). Mas plugin oficial mantido + docs claras.

## 4. Modelo de chaves

**Decisão: keys SÃO o source string** (Lingui default), não hierarquia
sintética tipo `settings.network.title`.

Vantagens:
- Source code permanece legível (sem indireção `t('foo.bar.baz')`).
- Falta de tradução cai no source PT-BR (default), não numa chave
  cryptic.
- Refactor de UI não força sync de keys.

Desvantagens:
- Mudança de copy em PT-BR força re-translate (mas com fuzzy match em
  catalog tools, custo baixo).

---

## 5. Pluralização PT-BR

PT-BR tem 2 forms (singular/plural). Crítico em:
- Contadores: "1 post" vs "5 posts", "1 hora atrás" vs "5 horas atrás"
- Listas: "1 follow" vs "N follows"
- Errors: "1 relay falhou" vs "N relays falharam"

Lingui ICU plural: `{count, plural, one {# post} other {# posts}}`.

Hoje a base usa concatenação manual (`${n} posts`) — funciona em PT mas
quebra em idiomas com 3+ plural forms (russo, árabe, polonês).

---

## 6. RTL — escopo Phase 2

Árabe + hebraico exigem:
- `dir="rtl"` no `<html>` (Tailwind suporta via `rtl:` prefix)
- Inversão de ícones direcionais (← → para → ←)
- Layout flex-reverse em listas
- Audit de hardcoded `text-right`/`text-left`

**Decisão: defer pra Phase 2.** Phase 1 cobre PT-BR + EN + ES (LTR
languages), wins sem custo grande de audit RTL.

---

## 7. Onde guardar strings

**Decisão: catalog files por locale em `src/locales/<lang>/messages.po`**
(Lingui default formato gettext-PO).

Estrutura:
```
src/locales/
├── pt-BR/messages.po   (source — sempre 100%)
├── en-US/messages.po
├── es-ES/messages.po
└── ar-SA/messages.po   (Phase 2)
```

PO format wins:
- Editor support nativo (Poedit, Lokalize, web tools)
- diff-friendly em git
- Comments + plurals como first-class
- Compatível com plataformas de tradução (Crowdin, Weblate, Lokalise)

Build step gera `.js` runtime artifacts via `lingui compile`.

---

## 8. Workflow de tradução

**Decisão fase 1: comunidade-driven via Weblate self-hosted.**

Razões:
1. **Manifesto §17 (sem chave mestra):** plataforma de tradução não
   pode ser proprietary (Crowdin SaaS daria controle a 3rd party).
   Weblate self-host = run-your-own (compatible §17).
2. **Manifesto §28 (privacy):** Weblate suporta auth via SSO/LDAP/
   passkey — sem exposição de tradutores.
3. **Cost zero** — Weblate AGPL, roda em VPS pequeno.
4. **Workflow paralelo ao código:** PRs no GitHub abrem auto-sync
   pra Weblate via webhook.

Phase 1.5: aceitar contributions via PR manual também (low-barrier
pra devs já familiarizados com gettext).

Machine-translate (DeepL/Google) **off-limits** pro client oficial —
viés de tradução automática introduz nuances que podem alterar
significado de termos sensíveis (privacidade, censura, etc.).
Plugins podem oferecer, mas default = human.

---

## 9. Detecção de idioma

**Decisão: 3-tier fallback**

1. `user_prefs.locale` (override explícito do user) — primeira escolha
2. `navigator.languages[0]` (negociação BCP-47 vs catalogs disponíveis)
3. `pt-BR` (source language, fallback duro)

Setting em SovereigntyCard ou novo `LanguageCard` — user vê override
explícito + lista de locales disponíveis com % completion.

Crítico: **NUNCA exportar locale via Nostr event** (manifesto §28 —
locale é fingerprint geográfico). Field local-only no `user_prefs`.

## 10. Custo estimado

### Phase 1 (PT-BR + EN + ES, sem RTL)

- **Setup Lingui + Vite plugin:** 1 dia (config, postcss, vite plugin,
  CI extract validation)
- **Audit + wrap strings em JSX:** ~5 dias (estimativa: ~400 strings
  user-facing entre components, dialogs, errors, toasts)
- **Tradução EN + ES initial:** ~2 dias (human, mas vocabulary técnico
  pequeno)
- **LOCK_VIA_TEST i18n-glossary-conformance:** 0.5 dia
- **Weblate setup:** 1 dia (VPS, AGPL stack, webhook GitHub)
- **Docs contributor (CONTRIBUTING-i18n.md):** 0.5 dia

**Total Phase 1: ~10 dias de trabalho.**

### Bundle impact

- Lingui core runtime: ~2 KB gz
- Catalog PT-BR (source, ~400 strings): ~6 KB gz
- Catalog EN: ~5 KB gz (loaded on-demand quando user troca)
- Total worst-case: ~13 KB gz extra entry chunk se carrega tudo eager.
  Lazy-load por locale: ~8 KB initial (Lingui + catalog do user).

Dentro do budget: ratchet hard cap atual 172 KB → 250 KB tem ~78 KB
folga. i18n consome ~8 KB → 86 KB folga remanescente.

### Phase 2 (RTL + plataforma adicional)

- Audit hardcoded direction classes: ~3 dias
- AR + HE traduções: dependem de tradutores comunidade
- Weblate moderation overhead: contínuo

## 11. Roadmap recomendado

**Fase 1A (próxima sprint, se decisão go):**
- Lingui + Vite plugin install
- Vite config + babel macros wiring
- `src/locales/` scaffold com PO files vazios
- Audit + wrap dos primeiros 50 strings (high-traffic: feed, post
  actions, onboarding) — proof of concept
- LOCK_VIA_TEST: i18n-glossary-conformance trava SPREAD/BURY/NIP-*
- Conformance ratchet: count de strings com `t\`...\`` macro >= 50

**Fase 1B (sprint seguinte):**
- Audit + wrap remaining ~350 strings
- EN-US tradução completa (human, Robin can dispatch)
- ES-ES tradução completa (community via Weblate)
- LanguageCard em Settings (user override + completion %)
- Locale detection 3-tier wiring
- Conformance ratchet: 100% strings wrapped (hard enforce)

**Fase 2 (depois de Phase 1B estabilizar):**
- AR + HE (RTL) — audit + traduções
- Plural forms para russo/polonês se demanda surge
- Plugin marketplace pra machine-translate opcional (off-default)

## 12. Riscos & mitigações

1. **Lock-in Lingui macros** — se LinguiJS abandonar manutenção,
   migração pra react-i18next via codemod é viável (~1 sprint).
   Mitigação: source strings em PT-BR são portáveis; catalog PO files
   funcionam com qualquer engine gettext-compatible.

2. **Bundle bloat se locales não lazy-load** — Phase 1 hard requirement:
   carregar SÓ o catalog do user, outros sob demanda. CI fail se
   default bundle inclui > 1 catalog.

3. **Glossário protocolar adulterado** — LOCK_VIA_TEST cobre. Audit
   PR template requer revisão de qualquer PO file por revisor que
   leu manifesto §29.

4. **Weblate self-host overhead operacional** — VPS small (~$5/mo)
   suporta. Backup catalogs em git via auto-PR semanal.

5. **Tradutores comunidade introduzem ideologia** — Drift é
   politicamente sensitive (anti-censura, privacy). Risco de
   tradução "suavizar" copy em locales onde regime é repressivo.
   Mitigação: revisão obrigatória por 2+ approvers + guidelines
   em `Docs/contributing-i18n.md` enfatizando fidelity.

## 14. Conclusão

i18n é **viável agora** com custo previsível (~10 dias Phase 1, +8 KB
bundle). LinguiJS v4 é a escolha tecnicamente correta. Weblate self-host
respeita manifesto §17 + §28. LOCK_VIA_TEST trava glossário protocolar.

**Recomendação Robin: agendar Phase 1A pra próxima sprint disponível**,
não bloquear release atual (PT-BR-only é viável pra MVP global se a
audiência inicial é Brasil+PT-falantes).

Recomendação Ted: NÃO shipping Phase 1 incompleto. Audit gradual de 50
strings/sprint cria estado intermediate (some PT, some wrapped) que é
pior que all-or-nothing — debugging confuso, traduções partial-
applied. Wrap completo em 1 sprint dedicada > wrap 30% em 3 sprints.

Recomendação Lily: LanguageCard precisa estar em Settings > "sistema"
group, posicionado próximo a SovereigntyCard (ambos são "ajustes de
